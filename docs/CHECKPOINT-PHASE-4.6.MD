## 2. هرم الأدوار — الفرق الذي لم يكن موجوداً

### 2.1 الأدوار السبعة

`admin` و`super_admin` كانا `['*']` حرفياً — دورين بأسمين وصلاحيات متطابقة. الآن:

| الدور | النطاق | ما يميّزه |
|---|---|---|
| `developer` (مبرمج) | **عابر للمعاهد** | كل الصلاحيات، وهو الوحيد الذي يملك `system.debug` |
| `super_admin` (المشرف الأعلى) | **عابر للمعاهد** | كل الصلاحيات **عدا** `system.debug` |
| `admin` (مدير معهد) | معهد واحد | كل الصلاحيات **عدا** `system.debug` و`institutes.manage` |
| `supervisor` · `teacher` · `guardian` · `student` | معهد واحد | كما كانت |

البذرة تعبّر عن هذا بثابت `WITHHELD` لا بثلاث قوائم صلاحيات متوازية — فما يميّز الأدوار الثلاثة
سطران اثنان، لا 39 سطراً مكرّراً ثلاث مرّات:

```php
private const WITHHELD = [
    'super_admin' => ['system.debug'],
    'admin'       => ['system.debug', 'institutes.manage'],
];
```

### 2.2 🔄 «عابر للمعاهد» — انحراف إلزامي عن الخطة

الخطة نصّت على إسناد الدورين العابرين بـ `institute_id = null`. **هذا مستحيل على هذا المخطّط:**

```sql
CREATE TABLE "model_has_roles" (
  "role_id" integer not null, "model_type" varchar not null, "model_id" integer not null,
  "institute_id" integer not null,                                   -- ← not null
  primary key ("institute_id", "role_id", "model_id", "model_type")  -- ← وجزءٌ من المفتاح الأساسي
)
```

العمود `not null` **وجزءٌ من المفتاح الأساسي**، وهذا مخطّط spatie نفسه لا اجتهاد منّا. جعله `nullable`
كان يتطلّب إعادة بناء الجدول، ويظلّ **مستحيلاً على MySQL** أصلاً (لا NULL في مفتاح أساسي) — والانتقال
إلى MySQL مطروح قبل المرحلة 9 (§13 في الخطة).

**المنفَّذ:** مفتاح فريق مُصطلَح عليه، `User::GLOBAL_TEAM_ID = 0` — ولا معهد بالمعرّف صفر. لا قيد
مفتاح أجنبي على العمود (القيد الوحيد على `role_id`)، فالقيمة سليمة على SQLite وMySQL معاً بلا migration.

```php
public const GLOBAL_TEAM_ID = 0;
public const GLOBAL_ROLES = ['developer', 'super_admin'];

$user->assignGlobalRole('super_admin');   // يضبط الفريق 0 ثم يعيده كما كان
$user->hasGlobalRole();                   // استعلام مباشر على model_has_roles
```

`globalRoleNames()` تستعلم `model_has_roles` مباشرةً لا عبر علاقة spatie — تلك مقيّدة بالمعهد الحالي
بحكم وضع الفرق فلا ترى الإسناد العابر أبداً. والنتيجة **محفوظة في خاصية للطلب الواحد**: `Gate::before`
يُستدعى مع كل فحص صلاحية، ولا يصحّ أن يضرب قاعدة البيانات في كل مرّة.

**الفهرس الذي طلبته الخطة موجود سلفاً** (`model_has_roles_team_foreign_key_index` في migration
`create_permission_tables`) — فلا migration في هذه المرحلة.

### 2.3 `Gate::before` — ونقطتان دقيقتان

```php
Gate::before(function (User $user, string $ability): ?bool {
    if ($user->hasGlobalRole('developer')) {
        return true;
    }

    if ($user->hasGlobalRole('super_admin') && $ability !== 'system.debug') {
        return true;
    }

    return null;
});
```

1. **`null` لا `false`.** إرجاع `false` من `Gate::before` يُنهي الفحص ويمنع الجميع — لا يعني «لا رأي لي».
2. **`system.debug` تسقط إلى الفحص المعتاد للمشرف الأعلى**، فيردّها دورُه الذي لا يملكها. لولا هذا
   الاستثناء لألغى `Gate::before` الفرقَ الوحيد بين الدورين ورأى المشرفُ الأعلى قسمَ «النظام».

## 3. حماية اللوحة — الثغرة القائمة وسدّها

### 3.1 المشكلة الحقيقية التي لم تكن في الخطة

وضع `permission:` على المسارات **وحده لا يكفي ويكسر كل شيء**: أدوار المستخدم مسنَدة داخل معهد،
وفحصُ spatie لا يراها ما لم يُضبط مفتاح الفريق — وضبطُه كان يقع داخل الخاصية المحسوبة `institute`
في مكوّن Livewire، أي **بعد** الـ middleware بمراحل. النتيجة كانت ستكون 403 للجميع بلا استثناء.

**الحلّ:** `App\Http\Middleware\SetPanelInstituteScope` مُلحقٌ بمجموعة `web` — نظير
`SetApiInstituteScope` القائم للـ API. يحسم المعهد ويضبط مفتاح الفريق قبل أن يصل الطلبُ إلى
`permission:`. ويبقى `bootedInteractsWithInstitute()` لطلبات Livewire التي لا تمرّ بطريق مسمّى.

خلافاً للـ API لا يَرفض هذا الوسيطُ من لا معهد له: لوحة المعلومات وصفحات الحساب الشخصي تعمل بلا معهد،
والرفض موضعه فحصُ الصلاحية على الطريق نفسه.

### 3.2 خريطة الصلاحيات على المسارات

| المسارات | الصلاحية |
|---|---|
| `dashboard` | — (كل مستخدم موثَّق؛ محتواها مشتقّ من صلاحياته) |
| `institute`, `settings/custom-fields`, `settings/traits` | `settings.manage` |
| `courses`, `shifts` | `courses.manage` |
| `circles*` | `circles.manage` |
| `students*` | `students.manage` |
| `teachers` | `teachers.manage` |
| `curricula` | `curricula.manage` |
| `attendance*` | 🔄 `attendance.take` (لا `attendance.view` — §3.3) |
| `excuses` | `excuses.review` |
| `reports*`, `stats` | `reports.view` |
| `institutes*` | `institutes.manage` |
| `users` | `users.manage` |
| `system/*` | `system.debug` |

والقائمة الجانبية غُلِّفت بـ `@can`/`@canany` مطابقةً لهذه الخريطة — لا تجميلاً: بدونها يرى المستخدمُ
روابطَ تؤدّي به إلى 403، فتصير الأدوار مفاجأةً بدل أن تكون شكلاً للوحة يفهمه من نظرة.

### 3.3 🔄 انحراف عن جدول الخطة: `attendance.take` لا `attendance.view`

الخطة نصّت على `attendance.view` لشاشات التفقّد. لكنّ `attendance.view` يملكها **الطالب وولي الأمر**
أيضاً (يريان حضورهما في تطبيقات فلاتر)، فحراستها بها كانت **تفتح لوح تفقّد المعهد كلّه لطالب** — وهو
عين ما تقول مقدّمة الخطة إنها جاءت لتمنعه. و`attendance.take` هي بالضبط حدّ «طاقم المعهد»:
يملكها الأستاذ والمشرف والمدير، ولا يملكها الطالب ولا ولي الأمر.

### ⚠️ 3.4 بقيّة مفتوحة تحتاج قرارك

دور **ولي الأمر يحمل `reports.view`** في كتالوج الأدوار منذ المرحلة الأولى، فهو — باتّباع جدول الخطة
حرفياً — يستطيع فتح شاشتَي «التقارير» و«الإحصائيات» في اللوحة ورؤية ترتيب حلقات المعهد كلّه.
الطالب محجوب (لا يملك `reports.view`).

لم أغيّرها لأن إغلاقها ليس تعديل مسارٍ بل قرارٌ في الكتالوج، وله طريقان:

1. نزع `reports.view` من دور `guardian` — الـ API لا يستعملها إطلاقاً (تأكّدتُ: لا وجود لها في
   `routes/api.php` ولا في المتحكّمات)، فالكلفة صفر عملياً.
2. أو إضافة صلاحية `reports.panel` للطاقم وحده.

عملياً لن يفتح ولي أمر اللوحة أصلاً (تطبيقه هو واجهته)، لكن الثغرة قائمة نظرياً.

## 4. `PanelScope` — وسدّ تسريب «أوّل معهد فعّال»

`InteractsWithInstitute::resolveInstitute()` كانت تسقط لمن لا معهد له إلى **أوّل معهد فعّال** — تسريبٌ
عبر المعاهد يُدخل الطالبَ وولي الأمر إلى بيانات معهد لا صلة لهما به. والنظير في الـ API
(`ApiScope`) كان يرفض هذه الحالة بـ 422 عمداً، وتعليقه يقول ذلك صراحةً منذ المرحلة الرابعة.

حُسم المنطق في `App\Support\PanelScope` ليتشاركه الوسيطُ والمكوّن، والسقوط الافتراضي **اقتصر على من
يملك دوراً عابراً للمعاهد** — وهو يرى المعاهد كلها على أي حال:

| الدالة | الغرض |
|---|---|
| `resolve()` | معهد الجلسة (إن بقي من حقّه) ← معهد سجلّ المستخدم ← السقوط المسموح |
| `switchTo()` | التبديل، ويُرفض معهدٌ لا دور للمستخدم فيه ولا سجلّ |
| `canAccess()` · `instituteIdsFor()` | المعاهد التي للمستخدم فيها سجلّ أو دور مسنَد |
| `institutesFor()` | ما يعرضه المبدّل — كل المعاهد للعابر، وما يخصّه لغيره |
| `homeInstitute()` | المعهد الأصلي، وعليه يقوم شريط التنبيه |
| `activate()` | الجلسة + `setPermissionsTeamId` معاً — لا ينفصلان |

**ومعهد الجلسة الذي لم يعد من حقّ المستخدم لا يُترك ليُعاد استعماله**: يُنسى من الجلسة فوراً.

`requireInstitute()` تحوّل الآن من لا معهد له إلى `institutes.index` إن كان يملك إنشاء المعاهد،
وإلى لوحة المعلومات وإلا. و`<x-no-institute>` صارت حالتين: «لا يوجد معهد بعد + زرّ إنشاء» لمن يملك،
و«حسابك غير مرتبط بمعهد» لمن لا يملك — وهي الحالة التي كان السقوط الافتراضي يخفيها.

## 5. CRUD المعاهد والمبدّل

### 5.1 الشاشات

- **`pages/institutes/index`** — جدول بالشعار والاسم والحلقات والطلاب والأساتذة والدورة الجارية
  والحالة، وإجراءات: **دخول كـ** · تعديل · تعطيل/تفعيل · حذف ناعم.
  **المعهد الذي تعمل فيه الآن لا يُحذف** — بدّل إلى غيره أولاً؛ وإلا سُحب البساط من تحت الجلسة نفسها.
- **`pages/institutes/form`** — إنشاء وتحرير. **لا تستعمل `InteractsWithInstitute` عمداً**: هذه
  الشاشة تحرّر معهداً بعينه لا «المعهد العامل»، وربطُها بالجلسة كان سيُبدّل السياق بمجرّد فتح معهد
  آخر للتعديل.
- **`pages/institutes/overview`** — لوحة المقارنة (§7).

### 5.2 النموذج المشترك — بلا تكرار

الشاشتان (`institute/edit` لمدير المعهد و`institutes/form` للمشرف الأعلى) تحرّران **نفس النموذج
بنطاقين مختلفين**، فاستُخرج ما يجمعهما إلى موضعين لا أكثر:

- `components/institute-form-fields.blade.php` — الحقول.
- `App\Support\InstituteForm` — القواعد (`rules`)، والتسميات، و`attributesFor()` التي تدمج
  `settings['points']` وتخزّن الشعار.

بدونهما كان النموذجان سيتفرّعان عند أوّل تعديل، فيصير للمعهد نموذجان.

### 5.3 `CreateInstitute` — الدورة الأولى ليست ترفاً

كل الشاشات التشغيلية مشتقّة من `currentCourse`، والمعهد الفارغ يستقبل صاحبه بستّ شاشات تقول «لا توجد
دورة جارية». فالإجراء يبذر **دورة أولى `draft`** — مسودّةً لا جاريةً، فالتواريخ والدوامات قرارُ صاحب
المعهد. (المناهج العامة والصفات الافتراضية متاحة تلقائياً بحكم استعلاماتها `institute_id IS NULL`،
فلا بذر لها.)

### 5.4 المبدّل والشريط

`livewire/institute-switcher` في رأس الشريط الجانبي، **ولا يظهر إلا لمن له أكثر من معهد** — ولمستخدم
المعهد الواحد (وهم الأغلبية) لا وجود له، فلا يوحي بخيار لا يملكه. التبديل يمرّ بـ `PanelScope::switchTo`
ثم **إعادة تحميل كاملة** (`navigate: false`): كل الخصائص المحسوبة في اللوحة مشتقّة من المعهد، وإعادة
بنائها واحدةً واحدة أطول وأخطأ من رحلة شبكة واحدة.

و`<x-institute-banner>` شريطٌ ذهبي رفيع فوق كل شاشة حين يكون المعهد العامل ليس معهد المستخدم الأصلي.
ليس تزييناً: الخطأ الشائع في نظام متعدّد المعاهد هو **تحرير بيانات المعهد الخطأ بعد تبديل منسيّ**.

## 6. المستخدمون والأدوار

### 6.1 الشاشة

`pages/users/index` — الاسم · البريد · **الأدوار كشرائح، مع معهد كلٍّ منها** · السجلّ المرتبط
(أستاذ/ولي أمر/طالب) · التحقّق. وفلاتر: بحث · دور · معهد (يظهر للعابرين فقط).

`UserAdminQuery::roleAssignments()` تجلب إسنادات كل الصفحة **بضمّة واحدة** من `model_has_roles`.
ولا تُقرأ من `$user->roles`: تلك مقيّدة بالمعهد الحالي فتُظهر بعض أدوار المستخدم وتُخفي بقيّتها —
وهذه شاشةٌ غرضها بالضبط رؤية إسناداته كلها.

### 6.2 هرم الإسناد — حراسة على الخادم

`PanelRole` enum يرتّب الأدوار هرمياً (ترتيب الحالات هو الهرم)، و`AssignUserRole::assignableRoles()`
تُرجع ما رتبتُه ليست أعلى من رتبة المُسنِد. فمدير المعهد لا يصنع مشرفاً أعلى ولا مبرمجاً، والمشرف
الأعلى لا يصنع مبرمجاً.

**الحراسة في الإجراء لا في الواجهة.** القائمة تُبنى من `assignableRoles` كي لا يرى المستخدم ما لا
يملكه، لكن `assertAssignable()` تُستدعى داخل `AssignUserRole` و`RevokeUserRole` و`InviteUser` —
إخفاءُ الخيار ليس حماية، والطلب يصل إلى الخادم كيفما بُنيت الواجهة. ويُمنع المستخدم من سحب دوره من نفسه.

### 6.3 `InviteUser` — الربط بالسجلّ والرابط المنسوخ

- ينشئ الحساب بكلمة مرور عشوائية، ويُسند الدور (عابراً كان أو داخل معهد).
- **يربط بالسجلّ**: أستاذاً قائماً إن مُرِّر، وإلا أنشأ سجلاً بأدنى ما يلزم. هذا الربط ليس تحسيناً:
  نطاق المعهد في اللوحة والـ API مشتقٌّ منه، و`ApiScope` يرفض حساباً بلا سجلّ بـ 422 — أي أن تطبيقات
  فلاتر لا تفتح له أصلاً.
- **لا إرسال بريد** (لا قناة إرسال في المشروع): يُولَّد رابط `Password::createToken` ويُعرض **مرّةً
  واحدة** لينسخه المشرف بنفسه.

### 6.4 «إنشاء حساب دخول» من شاشة الأساتذة

زرّ في قائمة إجراءات الأستاذ (خلف `users.invite`، ويظهر لمن لا حساب له) يفتح مودالاً بالبريد وحده
ويستدعي `InviteUser` بسجلّ الأستاذ — **وهذا شرط تشغيل تطبيق الأستاذ في المرحلة الخامسة**.

> ⚠️ **تحذير موثَّق في docblock الاستعلام:** `InstituteAdminQuery` هو **الصنف الوحيد في المشروع الذي
> يتجاوز نطاق المعهد عمداً**. المشروع لا يستعمل global scopes (كل استعلام يفلتر `institute_id` بيده)
> فلا شيء يمنع التجاوز تقنياً — ولذلك بالضبط يلزم التنبيه: لا يُنسخ هذا النمط إلى استعلام يجب أن يبقى
> محصوراً بمعهد واحد.

**خمسة استعلامات مهما بلغ عدد المعاهد**، لا حلقةٌ عليها: الحضور باستعلام مجمّع واحد فوق
`circle_daily_stats` عبر `course_circles → courses`، والنقاط بأربعة استعلامات مجمّعة (تسميع · بنود
مناهج · تقديرية · حضور). ونقاط الحضور وحدها تحتاج إعدادات كل معهد، فتُطبَّق على صفوف مجمّعة بـ
(معهد، حالة) لا صفاً صفاً. واختبارٌ يثبت أن عدد الاستعلامات **لا يتغيّر بإضافة أربعة معاهد**.

## 10. مزالق تقنية وُوجهت

| المزلق | الحل |
|---|---|
| `model_has_roles.institute_id` **`not null` وجزءٌ من المفتاح الأساسي** — فإسناد الدور العابر بـ `null` كما نصّت الخطة مستحيل، ومستحيل على MySQL أبداً | مفتاح فريق مُصطلَح عليه `GLOBAL_TEAM_ID = 0`، بلا migration ولا كسر تنقّل (§2.2) |

| `Gate::before` كان سيمنح المشرفَ الأعلى `system.debug` فيلغي الفرق الوحيد بينه وبين المبرمج | استثناء صريح يُرجع `null` لهذه القدرة وحدها فتسقط إلى الفحص المعتاد |
| `use RuntimeException;` في مكوّن Livewire أحادي الملف ⇒ *The use statement with non-compound name has no effect* بمستوى `E_WARNING` ⇒ 500 | الصنف المُصرَّف يعيش في النطاق العام، فالاسم المجرّد يُحلّ صحيحاً بلا `use` |

## 12. الخطوة التالية

**المرحلة 5 — تطبيق الأستاذ (Flutter):** `packages/mousqe_core` ثم شاشات حلقاتي / تفقّد بضغطة واحدة /
تسميع / سجل الجلسات. وقد صار إنشاء حساب الأستاذ وربطه بسجلّه ممكناً من اللوحة — وهو ما كانت المرحلة
الخامسة تنتظره.

**للاستئناف السريع:**

```bash
cd d:\Development\Laravel\mousqe\backend
composer run dev              # serve + queue + vite
```

سيناريو تحقّق يدوي سريع للمرحلة:

1. `migrate:fresh --seed` ⇒ سبعة أدوار، وحسابات `admin@` و`super@` و`dev@mousqe.test`.
2. الدخول بـ `super@` ⇒ «الإدارة العليا» في القائمة، ولا قسم «النظام». أنشئ معهداً ثانياً ⇒ يُبذر معه
   دورة مسودّة ⇒ بدّل إليه من المبدّل ⇒ **الطلاب والحلقات فارغة (نطاق سليم) والشريط الذهبي ظاهر**.
3. الدخول بـ `dev@` ⇒ قسم «النظام» ظاهر بشاشاته الثلاث.
4. الأساتذة ⇒ «إنشاء حساب دخول» ⇒ انسخ الرابط ⇒ عيّن كلمة مرور ⇒ ادخل به ⇒ **الشريط الجانبي فيه
   التفقّد والأذونات والتقارير فقط**، و`/institute` يردّ 403.
5. أنشئ حساباً بدور «طالب» من شاشة المستخدمين ⇒ ادخل به ⇒ **الشريط شبه فارغ**، وكل شاشات الإدارة 403.
6. `POST /api/v1/...` بمستخدم بلا معهد ⇒ 422 كما كان (لا انحدار في الـ API).
