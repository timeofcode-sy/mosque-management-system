## 2. الحساب صار تابعاً لسجلّه لا أصلاً برأسه

هذا هو **الانقلاب الجوهري** في المرحلة. كان `InviteUser` ينشئ حساباً ثم يشتقّ منه سجلّاً بالحدّ
الأدنى (`Teacher::create(['display_name' => $user->name])`)، فيخرج سجلٌّ هزيل من حساب. الآن العكس:
السجلّ هو الأصل، والحساب يولَّد معه.

```
Student::create(...)  ──▶  StudentObserver::created  ──▶  GenerateAccount
                                                             ├─ Credentials::username(PanelRole::Student)  →  student1042
                                                             ├─ Credentials::password()                    →  84029317
                                                             ├─ AssignUserRole::system(...) داخل المعهد
                                                             └─ students.user_id = ...
```

### 2.1 لماذا مراقبُ نموذج لا استدعاءٌ من الشاشة؟

لأن الطلاب يدخلون النظام من أكثر من باب: استمارةُ التسجيل (`SaveStudentRegistration`)، وأولياء الأمور
يُنشَؤون **ضمنها** لا في شاشةٍ لهم، والبذور، وأيّ مسار مستقبلي للمزامنة أو الاستيراد. الاستدعاء من
الشاشات كان يعني أربعة مواضع اليوم وخامساً يُنسى غداً — فيخرج طالبٌ بلا حساب ولا يُكتشف إلا عند
شكوى وليّه.

المراقب عديم الأثر عند التكرار: `GenerateAccount` يعود بـ `null` لسجلٍّ مرتبطٍ أصلاً، فتعديلُ الاسم
لا يولّد حساباً ثانياً.

### 2.2 الشرط الوحيد للتخطّي

```php
/** الحساب بلا دوره لا يفتح شيئاً — فحيث لا أدوار مبذورة لا حسابات تولَّد */
if (! Role::query()->where('name', $role->value)->where('guard_name', 'web')->exists()) {
    return null;
}
```

هذا يبقي اختبارات النماذج التي لا تبذر الأدوار (`StudentTest`, `EnrollmentTest`, …) عاملةً كما هي —
وهو في الإنتاج شرطٌ لا يتخلّف، لأن `RolesAndPermissionsSeeder` جزءٌ من `DatabaseSeeder`.

### 2.3 حالة الحساب تتبع حالة سجلّه

| ما يقع للسجلّ | ما يقع للحساب |
|---|---|
| `status` ⇒ `withdrawn` / `graduated` / `suspended` / `left` | `is_active = false` |
| `status` ⇒ عودة إلى `active` | `is_active = true` |
| حذف لَيِّن (`SoftDeletes`) | `is_active = false` — **ولا يُحذف الحساب**: سجلّات الحضور والتلاوة معلّقة به |
| استرجاع | يُولَّد الحساب إن لم يكن، ثم يُوافق حالتَه |

## 3. اسم المستخدم وكلمة المرور

### 3.1 الصيغة

`بادئة الدور + رقم متسلسل`: `student1042` · `teacher1003` · `guardian1188` · `supervisor1000` ·
`admin1000` · `sadmin1000` · `dev1000`.

**التفرّد على مستوى النظام كلّه لا داخل المعهد** — واختيارٌ مقصود: اسم المستخدم مفتاح الدخول وحده،
ولو رُقّم داخل كل معهد لتصادم طالبان من معهدين على الاسم نفسه ولَما عرف الخادمُ أيَّهما يقصد.

والرقم يُستنبط من **أكبر اسم قائم للبادئة** لا من عدّ الصفوف: الحذف يترك ثغرات في العدّ فيعيد
استعمال اسمٍ سبق أن وُزّع في بطاقة.

### 3.2 الكلمة تُحفظ مرّتين — وهذا هو القرار الأثقل في المرحلة

| العمود | الشكل | الغرض |
|---|---|---|
| `password` | مُلبَّد (`hashed`) | المصادقة |
| `generated_password` | مشفَّر (`encrypted`) | الطباعة وإعادة التسليم |

بدون النسخة المقروءة تُعرض الكلمةُ مرّةً واحدة عند التوليد ثم تُنسى، فلا يبقى للمشرف إلا «إعادة
التوليد» كلما نسي طالبٌ كلمتَه — أي أن التصدير والطباعة لدفعةٍ كاملة يستحيلان بعد يوم الإنشاء.

ثمانية أرقام تعني `10⁸` احتمالاً فقط، وهو ضعفٌ نظري مقصود: الكلمة تُملى على طفل وتُطبع في بطاقة.
يقابله خنقُ محاولات الدخول القائم أصلاً (`RateLimiter::for('login')` — خمس محاولات في الدقيقة)،
وقفلُ الحساب فور انسحاب الطالب.

كلا العمودين خارج الإسناد الجَماعي: `generated_password` ليس في `#[Fillable]` ويُكتب بـ `forceFill`
صراحةً، وهو في `#[Hidden]` فلا يتسرّب في أي استجابة JSON.

### 3.3 من يبدّل كلمة مَن

```php
// User::managesOwnPassword()
foreach ($this->panelRoles() as $role) {
    if (! $role->isAdministrative()) {
        return false;   // أستاذ · ولي أمر · طالب
    }
}
return true;            // مبرمج · مشرف أعلى · مدير معهد · مشرف · بلا دور
```

حاملُ دورٍ مولَّد لا يبدّل كلمته بنفسه، وشاشةُ الأمان تعرض له لافتةً بدل الاستمارة (والاستدعاء
نفسه محروسٌ بـ `abort_unless` لا بإخفاء الحقل وحده). والسبب ليس التضييق: لو غيّرها صاحبُها لبطلت
النسخةُ المطبوعة بيد المشرف من حيث لا يدري أحد.

وحين يبدّل الإداريّ كلمته من شاشة الأمان تُمسح النسخة المشفَّرة (`generated_password = null`) — فما
اختاره بنفسه لا يطّلع عليه مشرف، والشاشة تعرض عنه «غيّرها صاحبها».

### 3.4 الحراسة رتبةٌ لا صلاحية وحدها

```php
// AssignUserRole::outranks()
return self::rankOf($actor) < self::rankOf($target);
```

`credentials.manage` تفتح البابَ، والرتبةُ تحدّ ما وراءه: لا يرى مشرفٌ كلمةَ مشرفٍ نظيره ولا يبدّلها،
ولا مديرُ معهدٍ كلمةَ مديرٍ مثله. والقيد نفسه يحكم **الرؤية** في `CredentialQuery`، فما لا يُبدَّل
لا يُعرض أصلاً.

## 4. الدخول باسم المستخدم

| الموضع | قبل | بعد |
|---|---|---|
| `config/fortify.php` | `'username' => 'email'` | `'username' => 'username'` |
| اللوحة | `Fortify` الافتراضي | `Fortify::authenticateUsing(...)` — يطابق `username` **أو** `email`، ويرفض المقفل |
| `POST /api/v1/auth/login` | حقل `email` | حقل `username` يقبل الاثنين، و`user.username` في الاستجابة |

البريد بقي مقبولاً بديلاً لمن له بريد — للإداريّ الذي اعتاده — لكنه لم يعد إلزامياً ولا مفتاحاً.
و`users.email` صار `nullable` مع بقاء فهرسه الفريد (تعدّد `NULL` مسموح في MySQL وSQLite معاً).

### 4.1 الحساب المقفل لا تنفعه جلسةٌ قائمة

فحصُ الدخول وحده لا يكفي: جلسة اللوحة تبقى، ورمزُ Sanctum في التطبيق يبقى صالحاً شهوراً، فطالبٌ
انسحب اليوم يظلّ يقرأ بيانات معهده حتى ينتهي رمزُه. لذلك `EnsureUserIsActive` على المجموعتين:

- **اللوحة:** خروجٌ وإبطال الجلسة وتحويل إلى `login` برسالة.
- **الـ API:** حذفُ الرمز الحالي و`403`.

### 4.2 التسجيل الذاتي أُزيل

`Features::registration()` وصفحة `pages/auth/register.blade.php` — لا معنى لهما مع التوليد الآلي،
وبقاؤهما بابٌ مفتوح لإنشاء حسابات بلا دور. صفحة الدخول تقول بدلاً منه: «الحسابات تُنشئها إدارة
المعهد».

## 5. الإنشاء اليدوي صار للأدوار الإدارية وحدها

القسمة كلها في سطرٍ واحد على `PanelRole`:

```php
public function isAdministrative(): bool
{
    return $this->linkedRecord() === null;   // مبرمج · مشرف أعلى · مدير معهد · مشرف
}
```

ومنها `AssignUserRole::creatableRoles()` — وهي ما تبنيه قائمةُ شاشة المستخدمين:

| الفاعل | ما يراه في قائمة الإنشاء |
|---|---|
| مبرمج | مبرمج · مشرف أعلى · مدير معهد · مشرف |
| مشرف أعلى | مشرف أعلى · مدير معهد · مشرف |
| **مدير معهد** | **مدير معهد · مشرف** |
| مشرف | — (لا يملك `users.manage` أصلاً) |

مدير المعهد ينشئ مديراً نظيره **لمعهده** (قائمة المعاهد عنده معهدُه وحده)، ويدير المشرفين. والمشرف
لا يدير مشرفين. ومحاولةُ إنشاء حساب `student` أو `teacher` من هذا الطريق تُرفض في `InviteUser` نفسه
لا في الواجهة:

> حسابات «طالب» يولّدها النظام مع سجلّها ولا تُنشأ من هنا.

وسقطت معها دالّة `InviteUser::linkRecord()` كلّها — لم يعد ثمّة حسابٌ يشتقّ سجلّاً.

## 6. شاشة «بيانات الدخول» وطريقا التسليم

المسار `/credentials` خلف `permission:credentials.export`، **مستقلٌّ عن شاشة المستخدمين** لأن
جمهوره غيرُ جمهورها: المشرف يطبع بطاقات حلقته ولا يملك `users.manage`.

- **المرشّحات:** الاسم/اسم المستخدم · الدور · حلقةُ الدورة الجارية.
- **الكلمات مخفيّة افتراضاً** (`••••••••`) وتُكشف بمفتاح واحد — الشاشة تُفتح أمام قاعةٍ فيها طلاب،
  وكشفُ عمودٍ كامل بلا قصد تسريبٌ لحلقةٍ بأكملها.
- **تبديل الكلمة** من الصفّ: كلمةٌ يكتبها المشرف أو ثمانيةُ أرقام يولّدها النظام.

والتسليم بطريقين، كلاهما يقرأ المرشّحات نفسها من الرابط ويمرّ بـ `CredentialQuery` نفسه فتنطبق
عليه قيود الرتبة والمعهد بلا تكرار:

| الطريق | المسار | ملاحظة |
|---|---|---|
| CSV | `credentials/export` | يبدأ بـ BOM (`\xEF\xBB\xBF`) — بدونه يقرأ إكسل العربيةَ طلاسمَ |
| بطاقات للطباعة | `credentials/print` | `x-report-sheet` نفسه المستعمل في بقيّة التقارير، عمودان بحدٍّ متقطّع |

## 8. أثر التغيير على ما كان قائماً

| الملف | ما تغيّر |
|---|---|
| `app/Models/User.php` | `allRoleNames()` · `panelRoles()` · `isAdministrative()` · `managesOwnPassword()` — و`globalRoleNames()` صارت تقرأ من `roleAssignmentQuery()` المشترك بدل تكرار الاستعلام |
| `app/Actions/AssignUserRole.php` | `system()` · `creatableRoles()` · `outranks()` — و`roleNamesOf()` صارت تفويضاً إلى `User::allRoleNames()` |
| `resources/views/pages/teachers/index.blade.php` | زرّ «إنشاء حساب دخول» بالبريد ⇐ «توليد حساب دخول» بلا حقول، ولا يظهر إلا لسجلٍّ بلا حساب |
| `resources/views/pages/users/index.blade.php` | عمود «البريد» ⇐ «اسم المستخدم» · «التحقّق» ⇐ «الحالة» · إقفال/فتح · توليد كلمة مرور |
| `database/factories/UserFactory.php` | `username` تلقائي + حالة `inactive()` |

**فخّ استُدرك:** `User::factory()->create()` لا يقرأ قيمةَ العمود الافتراضية من قاعدة البيانات، فكان
`is_active` يعود `null` على النموذج الطازج فيحسبه `EnsureUserIsActive` مقفلاً ويطرد المستخدم فوراً.
الحلّ `protected $attributes = ['is_active' => true]` على النموذج نفسه لا في المصنع وحده.

## 9. الخطوة التالية

**المرحلة 5 — تطبيق الأستاذ (Flutter):** عقد الدخول صار نهائياً (`username` + كلمة، ورمز Sanctum)،
والحساب مضمونُ الوجود لكل أستاذ وطالب وولي أمر — وهو ما كانت المرحلة الخامسة تنتظره.

**للاستئناف السريع:**

```bash
cd d:\Development\Laravel\mousqe\backend
composer run dev              # serve + queue + vite
```

سيناريو تحقّق يدوي:

1. `migrate:fresh --seed` ⇒ **243 حساباً كلّها باسم مستخدم**، لا واحد مقفل.
2. الدخول بـ `admin1000` / `password` ⇒ «بيانات الدخول» في قسم «الأشخاص».
3. سجّل طالباً جديداً ⇒ افتح «بيانات الدخول» ⇒ **اسمه وكلمته موجودان بلا خطوة إضافية**، وأبوه وأمّه
   معه.
4. اكشف الكلمات ⇒ صدّر CSV ⇒ افتحه في إكسل ⇒ **العربية سليمة**. ثم اطبع البطاقات.
5. ادخل بحساب الطالب ⇒ `/settings/security` ⇒ **لافتة بدل استمارة كلمة المرور**، و`/credentials` يردّ 403.
6. أعد الطالب إلى «منسحب» ⇒ حاول الدخول بحسابه ⇒ **مرفوض**، ورمزُه في التطبيق يسقط عند أول طلب.
7. من شاشة المستخدمين بحساب مدير معهد ⇒ «حساب جديد» ⇒ **القائمة فيها «مدير معهد» و«مشرف» لا غير**.
