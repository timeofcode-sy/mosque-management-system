## 2. إعادة الهيكلة: Actions + Queries

**السبب:** ملاحظةٌ في المراجعة أن ملفات الشاشات تحمل منطقاً واستعلامات.

**القاعدة المعتمدة:** *كل كتابة تمرّ بـ `app/Actions/`، وكل قراءة تمرّ بـ `app/Queries/`.*
ملف الشاشة يحمل حالة الواجهة وربطها فقط.

```php
// قبل — استعلام داخل ملف Blade
#[Computed]
public function students(): LengthAwarePaginator
{
    return Student::query()
        ->where('institute_id', $this->institute->id)
        ->when($this->search !== '', fn ($q) => $q->where(...))   // 20 سطراً
        ->paginate(20);
}

// بعد
#[Computed]
public function students(): LengthAwarePaginator
{
    return $this->query()->paginate($this->institute, $this->search, $this->status, $this->courseCircleId);
}
```

**التحقّق:**

```bash
grep -rn "::query()\|->whereHas(\|->withCount(\|->paginate(" resources/views/pages/ --include=*.blade.php
# لا نتائج خارج auth/ و settings/ الموروثتين
```

### 2.1 لماذا لا يوجد `Controller` لكل شاشة؟

المشروع على **Livewire 4**، حيث المكوّن *هو* المتحكّم: الطلب يصل إليه مباشرةً عبر
`Route::livewire()`، ولا يمرّ بأي متحكّم. وضع `Controller` بجانبه يُنتج طبقةً ميتة لا يمرّ بها طلب.

المتحكّم الوحيد `ReportPrintController` له مبرّر حقيقي: صفحات الطباعة استجاباتُ HTTP ساكنة
بلا حالة ولا تفاعل، فلا معنى لجعلها مكوّنات Livewire.

### 2.2 لماذا `Queries` لا `Repositories`؟

Eloquent نفسه طبقةُ تجريد فوق قاعدة البيانات. تغليفه بـ `Repository` + `Interface` يعني ثلاثة
ملفات لكل استعلام مقابل قابلية تبديلٍ لن تُستعمل (لن نستبدل Eloquent). صنف الاستعلام يعطي
الفصل والاختبار نفسيهما بملف واحد.

### 2.3 حقن الاعتماد في مكوّن Livewire

طبقة القراءة تُحلّ من الحاوية داخل دالة خاصّة، **لا** بالحقن في المُنشئ:

```php
private function query(): AttendanceBoardQuery
{
    return app(AttendanceBoardQuery::class);
}
```

مكوّن Livewire يُعاد بناؤه مع كل طلب (hydration)، والمُنشئ ليس موضع اعتماد. الأصناف عديمة الحالة
فلا كلفة في حلّها. الإجراءات في دوال الأفعال تُحقن بالطريقة الموثّقة: `public function save(SaveX $action)`.

## 5. الإحصاء والترتيب

```
النسبة = (حاضر + متأخّر) ÷ (المجموع − المأذون)
```

الإذن المسبق لا يُحسب غياباً على الحلقة، وإلا عاقب الترتيبُ الحلقةَ على ظرف خارج يدها.
والجلسة التي كلُّ طلابها مأذونون تُعطى صفراً لا قسمةً على صفر.

**الترتيب** بين حلقات الدوام نفسه: بالنسبة نازلاً، ويفصل التعادلَ عددُ الحاضرين ثم معرّف الحلقة
لثبات النتيجة. المتعادلتان تأخذان الرتبة نفسها والتالية تقفز (1، 1، 3).

**الحساب متزامن لا في طابور** — خلافاً لما اقترحته الخطة. الشاشة تعرض النسبة والترتيب فور
الإغلاق، وكلفته استعلاماتٌ معدودة على نطاق دوامٍ واحد في يومٍ واحد. وللبناء الشامل بأثر رجعي:

```bash
php artisan mousqe:recalculate-stats [--course=ID]
```

## 6. خللان حقيقيان اكتُشفا وأُصلحا

### 6.1 زر «تعديل» يفتح نافذة 404 — *ما بلّغ عنه العميل*

`App\Concerns\HasUuid` يجعل `getRouteKeyName()` يعيد `uuid`، بينما كانت الواجهات تمرّر
`{{ $model->id }}`. فيرفع Livewire `ModelNotFoundException` ← 404 يعرضه في نافذة بدل النافذة المنبثقة.

أصاب **22 زرّاً في 9 شاشات** — كل أزرار التعديل والحذف والأرشفة والنقل. أُصلح بتمرير
`'{{ $model->uuid }}'`، ويحرسه `tests/Feature/Livewire/RowActionsTest.php` (9 اختبارات).

### 6.2 الترتيب اليومي مقلوب

ظهر أثناء التحقّق من البذور: حلقة بنسبة **100%** تحمل الرتبة **3**.

السبب: `Collection::sortBy()` بمصفوفة إغلاقات يستدعي كل إغلاق **مقارِناً** بوسيطين `($a, $b)`
لا مستخرِجَ مفتاح (`Collection.php:1639`). والإغلاق أحاديّ الوسيط يتجاهل `$b` ويعيد قيمةً ثابتة
الإشارة، فيصير المقارِن غير متّسق وتبقى المجموعة **بترتيب الإدخال بلا ترتيب أصلاً**.

```php
// قبل — يبدو سليماً ويصمت عن الخطأ
->sortBy([fn ($s) => -(float) $s->attendance_rate, fn ($s) => -(int) $s->present])

// بعد — مقارِن صريح
->sort(fn ($a, $b) => [(float) $b->attendance_rate, (int) $b->present, (int) $a->course_circle_id]
                  <=> [(float) $a->attendance_rate, (int) $a->present, (int) $b->course_circle_id])
```

تحقّقنا أن الاختبار يمسك الخلل: بإرجاع الشيفرة المعطوبة يفشل `test_the_highest_rate_ranks_first_even_when_created_last`
بـ «3 ليست 1»، وبإعادة الإصلاح ينجح.

## 7. خلل بنيوي في المخطط: أعمدة التاريخ

`updateOrCreate` على `circle_daily_stats` كان يخرق قيد `unique(course_circle_id, date)`.

**السبب:** صيغة `'date:Y-m-d'` في `casts()` تحكم التسلسل إلى JSON فقط؛ أما الكتابة فتمرّ بـ
`fromDateTime()` فتُخزَّن `Y-m-d H:i:s`. فتمرير Carbon يكتب `"2026-08-18 00:00:00"` وتمرير نصّ
يكتب `"2026-08-18"` — ولا يتطابقان.

أصاب **22 عموداً في 14 نموذجاً** (كل أعمدة `$table->date()`). أُصلح بـ `App\Casts\DateOnly`
الذي يُطبّع الكتابة دائماً إلى `Y-m-d`.

> ⚠️ **يهمّ المرحلة 4:** مقارنة التواريخ في المزامنة كانت ستُخفق بالطريقة نفسها.

## 9. مزالق تقنية وُوجهت

| المزلق | الحل |
|---|---|
| `{{ '{{'.$var.'}}' }}` في Blade — القوسان الداخليان يُنهيان التعبير فينكسر التصريف | `@{{ {{ $variable }} }}` |
| `sortBy([closure, closure])` يعامل الإغلاق مقارِناً لا مستخرِجَ مفتاح | مقارِن صريح بـ `sort()` — §6.2 |
| صيغة `date:Y-m-d` لا تحكم الكتابة إلى القاعدة | cast مخصّص `DateOnly` — §7 |
| Pint يحذف `use` الخاص بـ cast مشار إليه داخل مصفوفة نصّية | إدراج الاستيراد بعد `namespace` ثم إعادة Pint |
| `Route::livewire` لا يقبل متحكّماً | `Route::get` + `ReportPrintController` لصفحات الطباعة |
